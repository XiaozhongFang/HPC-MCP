# HPC-MCP のアーキテクチャ

他の言語：[English](../ARCHITECTURE.md) | [简体中文](../zh-CN/ARCHITECTURE.md) | [한국어](../ko/ARCHITECTURE.md) | [繁體中文](../zh-TW/ARCHITECTURE.md)

HPC-MCP は stdio の MCP サーバです。stdout に書き出されるのは MCP プロトコルだけで、
診断や監査の記録は stderr または設定されたログファイルに出力されます。

```text
MCP client
   |
   v
server.py（ディスパッチ、実行時引数の形状、監査、ライフサイクル）
   |
   +--> tools/registry.py（公開ツールのスキーマとアダプタ）
   |       |
   |       +--> security/*（純粋なポリシー判定）
   |       +--> filesystem / shell / slurm services
   |       +--> cluster/topology.py（計算ノードの収集ジョブ + sinfo、キャッシュ付き）
   |
   +--> ssh/manager.py と ssh/sftp.py（固定 argv、プロセスは有界）
               |
               v
          設定された 1 台の HPC ホスト
```

## リクエストの流れ

1. `server.on_call_tool` がツール名を解決し、オブジェクトでない引数、欠落、未知の引数を拒否します。
2. registry のアダプタがスカラ型を検証し、型を通った値だけを転送します。
3. リモート状態を変更するコマンドの実行前に、サービス層がポリシーを適用します：
   `path_policy` はリモートパスを canonical 化し、`command_policy` はログインノードのコマンドを分類し、
   `slurm_policy` はリソースを検証します。
4. サービス層は SSH transport に固定 argv、または信頼済みでクォート済みの内部ラッパーの実行を要求します。
   transport の出力はバイト上限までストリームされ、成功・失敗・タイムアウトのいずれでも子プロセスは回収されます。
5. 結果はテキストコンテンツとして返されます。すべての呼び出しには、再帰的な資格情報マスキングを伴う
   ALLOW/DENY の監査レコードが付きます。

## 分離境界

リモートの `root` はユーザー専用のディレクトリで、`/` にはできません。リモートパスは字句的な検査と
リモート `realpath` の両方で検証されます。作成系の操作では、既存のシンボリックリンクの宛先も拒否します。
転送ツールには独立したローカルの `local_root`（既定ではプロセスの作業ディレクトリ）があり、
シンボリックリンクの構成要素と資格情報系のファイル名を拒否し、転送後にサイズ上限を強制します。

ログインノードのコマンドは小さな許可リストです。シェル演算子、実行ファイルのパス、ネストしたシェル、
シンボリックリンクを追うオプション、Slurm を直接照会するコマンドは一切受け付けません。ジョブの照会は、
現在のプロセスセッションの `tool_session` エントリを検証する Slurm メソッドだけが公開します。
出力パスは数値の job ID と canonical なジョブディレクトリから導出され、信頼できないメタデータからは
決して導出されません。Slurm は出力を開く前に中間ディレクトリを作成できないため、まずフラットな
`%j.stdout.log`/`%j.stderr.log` に書き出します。その後サーバが canonical なジョブディレクトリを作成し、
それらのファイルをその配下にリンクします。

## クエリコストの境界

共有アカウントの安全性は、*他ユーザーのデータや大量のデータを MCP プロセスに一切読み込まない*
ことでもあります。

- **自所有のジョブだけを照会。** `status`/`queue`/投入時のアクティブジョブ数は
  `squeue -j <tracked ids>` のみを実行します。追跡中のジョブがなければ、その呼び出しは
  `squeue` を一切実行せずに戻ります。他ユーザーのジョブメタデータがプロセスに入ることはありません。
- **有界なファイル読み取り。** `hpc.files.read` は `files.max_read_slice_bytes`
  （既定 256 KiB）で上限を設けた 1 スライスを返します。ツールの説明は、EOF までページングする代わりに
  まず `hpc.files.search` を使うよう agent を導きます。
- **有界な再帰一覧。** `hpc.files.list` は 1 回のリモート呼び出しで 1 階層だけを列挙し、
  `head` でリモート出力を打ち切り（`bash -o pipefail` による SIGPIPE 検出）、
  `depth:N` カーソルで再開します。
- **有界な検索。** `hpc.files.search`（単一ファイル：stat して大きすぎるものは拒否。ツリー：
  `grep -rn` + 除外ディレクトリ + ファイルごとの `-m` + 全体の `head` + `timeout`）は、
  すべての予算がサーバ側でクランプされます。パターンはクォートされた grep の引数として渡り、
  制御文字は拒否されます。
- **高レベルツール。** `hpc.jobs.diagnose`（状態 + 会計 + 有界な末尾 + エラーシグネチャ）と
  `hpc.project.snapshot`（有界なツリー + git サマリ + 追跡中のジョブ）は、複数の低レベル呼び出しを
  1 回に集約し、各クエリは有界です。
- **トポロジ探索。** `hpc.cluster.topo` は `sinfo` のサマリ（すでに許可リスト済みで、
  `-p <allowed partitions>` に限定されるため、未許可のパーティションが応答に現れることはありません）と、
  計算ノード上で 1 CPU のジョブとして実行される**固定の、サーバ生成の**収集スクリプトを組み合わせます。
  ツールの引数がそのスクリプトに展開されることはなく、スクリプトはノードローカルのファイルのみを読みます
  ——`squeue`/`sacct`/`scontrol` を決して照会しないため、共有アカウントの分離ルールは計算側でも保たれます。
  結果はプロセス内と、`$ROOT/.hpc-mcp/topo/` 配下の JSON ファイルとして
  `topology.cache_ttl_seconds`（既定 24 h）のあいだキャッシュされ、待機中の収集ジョブが呼び出しごとに
  再投入されるのを防ぎます。`topology.wait_seconds` を超えて待機中の収集ジョブは
  `status: "pending"` を返して再利用され（最終的には取り消されることもあります）、重複投入はされません。
- **クエリキャッシュ。** 冪等な読み取り専用ツールは、`tool + 正規化した引数` で
  `cache_ttl_seconds`（既定 2 s、0 で無効）のあいだ重複排除されます。書き込み系ツールは
  キャッシュ全体を無効化します。

## 意図的に残るリスク（3 層）

| 層 | 強制機構 | 防ぐ対象 |
|---|---|---|
| 1. MCP policy | パスサンドボックス、コマンド許可リスト、Slurm リソースポリシー、ジョブ所有権、クエリ予算、監査 | 振る舞いの壊れた agent |
| 2. Slurm | パーティション許可リスト、リソース／同時実行の上限、唯一の `sbatch` 入口 | 計算資源の濫用 |
| 3. OS/クラスタ | 独立した Unix UID、Slurm のジョブ分離 + filesystem ACL、コンテナサンドボックス、または特権付きリモートヘルパー | *悪意あるコード*の分離 |

リモートホストは共有 Unix アカウントであるため、同等のアカウント権限を持つプロセスは
canonical 化と最終コマンドのあいだにパスの競合を起こせます。サーバはこの窓を最小化し、
シンボリックリンクの宛先を拒否しますが、競合を完全に排除するには `openat(2)`/`O_NOFOLLOW` を用いる
特権付きリモートヘルパー、またはユーザーごとの独立 Unix アカウントが必要です。同様に、
JSON の追跡ファイルは論理的なセッション境界であり、OS のアクセス制御境界ではありません。
同等の Unix アカウントはこれを読み書きできます。

決定的に重要なのは、`hpc.slurm.submit` が agent に、その Unix UID として計算ノード上でプログラムを
実行する能力を与えるという点です。Layer 1-2 は、その後にその UID が読めるすべてを読む悪意あるコードを
封じ込めることはできません。「明らかに悪意がある」Julia/Python を正規表現やポリシーでフィルタすることを、
OS レベルの分離機構として当てにしないでください。同一アカウントの悪意あるコードが脅威モデルに含まれる場合は、
Layer 3（独立 UID、ジョブ分離 + ACL、またはコンテナ／サンドボックス）を導入してください。
