# HPC-MCP 아키텍처

다른 언어: [English](../ARCHITECTURE.md) | [简体中文](../zh-CN/ARCHITECTURE.md) | [日本語](../ja/ARCHITECTURE.md) | [繁體中文](../zh-TW/ARCHITECTURE.md)

HPC-MCP는 stdio MCP 서버입니다. stdout에 기록되는 것은 MCP 프로토콜뿐이며, 진단과 감사 기록은 stderr 또는 설정된 로그 파일로 나갑니다.

```text
MCP client
   |
   v
server.py (디스패치, 런타임 인자 형태, 감사, 수명 주기)
   |
   +--> tools/registry.py (공개 도구 스키마와 어댑터)
   |       |
   |       +--> security/* (순수 정책 판단)
   |       +--> filesystem / shell / slurm services
   |       +--> cluster/topology.py (계산 노드 수집 작업 + sinfo, 캐시 사용)
   |
   +--> ssh/manager.py 와 ssh/sftp.py (고정 argv, 프로세스는 유계)
               |
               v
          설정된 단일 HPC 호스트
```

## 요청 흐름

1. `server.on_call_tool`이 도구 이름을 해석하고 객체가 아닌 인자, 누락, 알 수 없는 인자를 거부합니다.
2. registry 어댑터가 스칼라 타입을 검증하고 타입을 통과한 값만 전달합니다.
3. 원격 상태를 변경하는 명령 실행 전에 서비스 계층이 정책을 적용합니다:
   `path_policy`는 원격 경로를 canonical화하고, `command_policy`는 로그인 노드 명령을 분류하며,
   `slurm_policy`는 리소스를 검증합니다.
4. 서비스 계층은 SSH transport에 고정 argv 또는 신뢰할 수 있고 인용된 내부 래퍼의 실행을 요청합니다.
   transport 출력은 바이트 상한까지 스트리밍되며, 성공·실패·타임아웃 어느 경우에도 자식 프로세스는 회수됩니다.
5. 결과는 텍스트 콘텐츠로 반환됩니다. 모든 호출에는 재귀적 자격 증명 마스킹이 적용된
   ALLOW/DENY 감사 레코드가 함께 남습니다.

## 격리 경계

원격 `root`는 사용자 전용 디렉터리이며 `/`일 수 없습니다. 원격 경로는 어휘적 검사와 원격 `realpath` 검사를
모두 거칩니다. 생성 계열 작업은 이미 존재하는 심볼릭 링크 대상도 거부합니다. 전송 도구에는 독립적인 로컬
`local_root`(기본값은 프로세스 작업 디렉터리)가 있으며, 심볼릭 링크 구성 요소와 자격 증명 파일 이름을 거부하고
전송 후 크기 상한을 강제합니다.

로그인 노드 명령은 작은 허용 목록입니다. 셸 연산자, 실행 파일 경로, 중첩 셸, 심볼릭 링크를 따라가는 옵션,
Slurm을 직접 조회하는 명령은 전혀 허용되지 않습니다. 작업 조회는 현재 프로세스 세션의 `tool_session` 항목을
검증하는 Slurm 메서드로만 노출됩니다. 출력 경로는 숫자 job ID와 canonical 작업 디렉터리에서 도출되며
신뢰할 수 없는 메타데이터에서 도출되지 않습니다. Slurm은 출력을 열기 전에 중간 디렉터리를 만들 수 없으므로
먼저 평면적인 `%j.stdout.log`/`%j.stderr.log`에 기록하고, 이후 서버가 canonical 작업 디렉터리를 만들어
그 아래에 두 파일을 연결합니다.

## 쿼리 비용 경계

공용 계정의 안전성은 *다른 사용자의 데이터나 대량의 데이터를 MCP 프로세스에 아예 읽지 않는 것*이기도 합니다.

- **자기 소유 작업만 조회.** `status`/`queue`/제출 시의 활성 작업 수는
  `squeue -j <tracked ids>`만 실행합니다. 추적 중인 작업이 없으면 그 호출은
  `squeue`를 전혀 실행하지 않고 반환합니다. 타인의 작업 메타데이터는 프로세스에 들어오지 않습니다.
- **유계 파일 읽기.** `hpc.files.read`는 `files.max_read_slice_bytes`
  (기본 256 KiB)로 상한이 정해진 슬라이스 하나를 반환합니다. 도구 설명은 EOF까지 페이지를 넘기는 대신
  먼저 `hpc.files.search`를 쓰도록 agent를 유도합니다.
- **유계 재귀 나열.** `hpc.files.list`는 원격 호출 한 번에 한 계층만 열거하고,
  `head`로 원격 출력을 자르며(`bash -o pipefail`로 SIGPIPE 감지), `depth:N`
  커서로 이어서 진행합니다.
- **유계 검색.** `hpc.files.search`(단일 파일: stat 후 초과 시 거부, 트리:
  `grep -rn` + 제외 디렉터리 + 파일별 `-m` + 전역 `head` + `timeout`)의 모든 예산은
  서버 측에서 클램프됩니다. 패턴은 인용된 grep 인자로 전달되며 제어 문자는 거부됩니다.
- **고수준 도구.** `hpc.jobs.diagnose`(상태 + 회계 + 유계 꼬리 + 오류 시그니처)와
  `hpc.project.snapshot`(유계 트리 + git 요약 + 추적 중인 작업)은 여러 저수준 호출을 하나로
  합치며, 각 쿼리는 유계입니다.
- **토폴로지 탐색.** `hpc.cluster.topo`는 `sinfo` 요약(이미 허용 목록에 있고
  `-p <allowed partitions>`로 한정되므로, 허가되지 않은 파티션이 응답에 나타나지 않습니다)과
  계산 노드에서 1 CPU 작업으로 실행되는 **고정된 서버 생성** 수집 스크립트를 결합합니다.
  도구 인자가 그 스크립트에 삽입되는 일은 없으며, 스크립트는 노드 로컬 파일만 읽습니다
  ——`squeue`/`sacct`/`scontrol`을 결코 조회하지 않으므로 공용 계정 격리 규칙은 계산 측에서도 유지됩니다.
  결과는 프로세스 내부와 `$ROOT/.hpc-mcp/topo/` 아래의 JSON 파일로
  `topology.cache_ttl_seconds`(기본 24 h) 동안 캐시되어, 대기 중인 수집 작업이 호출마다
  다시 제출되는 것을 막습니다. `topology.wait_seconds`를 넘겨도 대기 중인 수집 작업은
  `status: "pending"`을 반환하고 재사용되며(결국 취소될 수 있습니다), 중복 제출되지 않습니다.
- **쿼리 캐시.** 멱등적 읽기 전용 도구는 `tool + 정규화된 인자`로
  `cache_ttl_seconds`(기본 2 s, 0이면 비활성) 동안 중복 제거됩니다. 쓰기 도구는
  캐시 전체를 무효화합니다.

## 의도적으로 남는 위험(3계층)

| 계층 | 강제 기구 | 방어 대상 |
|---|---|---|
| 1. MCP policy | 경로 샌드박스, 명령 허용 목록, Slurm 리소스 정책, 작업 소유권, 쿼리 예산, 감사 | 잘못 동작하는 agent |
| 2. Slurm | 파티션 허용 목록, 리소스/동시 실행 상한, 단일 `sbatch` 진입점 | 계산 자원 남용 |
| 3. OS/클러스터 | 독립 Unix UID, Slurm 작업 격리 + filesystem ACL, 컨테이너 샌드박스, 또는 권한 있는 원격 헬퍼 | *악성 코드* 격리 |

원격 호스트는 공용 Unix 계정이므로, 동등한 계정 권한을 가진 프로세스는 canonical화와 최종 명령 사이에
경로 경쟁을 일으킬 수 있습니다. 서버는 이 창을 최소화하고 심볼릭 링크 대상을 거부하지만, 경쟁을 완전히
제거하려면 `openat(2)`/`O_NOFOLLOW`를 사용하는 권한 있는 원격 헬퍼나 사용자별 독립 Unix 계정이 필요합니다.
마찬가지로 JSON 추적 파일은 논리적 세션 경계이며 OS 수준 접근 제어 경계가 아닙니다. 동등한 Unix 계정은
이 파일을 읽거나 수정할 수 있습니다.

결정적으로, `hpc.slurm.submit`은 agent에게 해당 Unix UID로 계산 노드에서 프로그램을 실행할 능력을
부여합니다. Layer 1-2는 그 UID가 읽을 수 있는 모든 것을 읽는 악성 코드를 봉쇄할 수 없습니다.
"명백히 악의적인" Julia/Python을 정규식이나 정책으로 걸러내는 것을 OS 수준 격리 기구로 의존하지 마세요.
동일 계정의 악성 코드가 위협 모델에 포함된다면 Layer 3(독립 UID, 작업 격리 + ACL, 또는 컨테이너/샌드박스)를
도입해야 합니다.
